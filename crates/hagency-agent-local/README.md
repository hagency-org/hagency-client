# Owner-local agent execution controls

This crate uses a new SQLite application ID and schema. It rejects old Hagency databases and permanently binds its database to the authenticated Matrix owner. It has no Fleet, Engagement, resource approval, transfer or server administrator interface.

The desktop host authenticates the owner through Pasion/Hagency, fetches an owner-scoped Agent/binding record from the server, and calls `register_binding`. Scope values must come from verified server envelopes and Matrix sender IDs, never model output or nicknames. A policy/approval UI must call owner-only APIs from the trusted desktop process; a model child process must not receive these APIs or the database path.

## Runtime contract

1. Budgets are optional limits. Missing Agent, Room and requester budgets default unlimited; the retained `Unset` encoding also means no limit. All configured limits intersect: the Agent total spans its Rooms, a Room total covers that Room, and a requester limit covers only that user in that Room. `Tokens(0)` stops new reservations; explicit request denial remains independent of token limits. Unlimited budgets still track spent and held usage, and missing usage settles as zero without blocking later work. Every layer defaults to denying high-risk tools; to enable a tool, configure all layers explicitly. `set_policy` is a compare-and-swap revision update requiring the authenticated local owner, with no server approval.
2. For each provider invocation, `reserve(scope, call_id, dispatch_id, verified_maximum_input_plus_output, unix_seconds)` atomically reserves three accounts. Only `Reservation::New` permits starting the provider. `AlreadyPending` must never restart the invocation. A retry which may incur another charge gets a fresh call ID under the original dispatch/requester. The adapter must expose an enforceable maximum; estimated-only adapters cannot claim strict quotas.
3. `settle` records provider input/output totals exactly once and refunds unused reservation. Cached input and reasoning output are subsets, not additional token charges. Changed usage cannot overwrite a prior settlement. Estimate overruns are charged honestly; subsequent requests use the configured remaining budget without creating a historical-error block.
4. On uncertain provider outcomes call `mark_unknown`; on exclusive execution-device restart call `recover_interrupted` before admitting work. Unreported usage is automatically settled as zero and releases the original reservation. Historical unknown calls are handled during exclusive Agent recovery or the next reservation; they do not block new work. Execution outcomes remain unknown and are never automatically replayed. Settlement always updates the invocation's original UTC day/month or lifetime accounts.
5. Use `context_key` for prompt history, retrieval indexes, result caches and tasks, and `context_session`/`set_context_session` for Codex sessions. These keys isolate owner, Agent, binding, Room, requester and thread. The key is a structured JSON tuple, not string concatenation. The host must apply equivalent scoping to filesystem/network capabilities; storing a session key alone does not isolate tools.
6. A dispatch snapshots its initial policy. Later widening cannot upgrade that dispatch; tightening applies to subsequent calls/tools. A period change conflicts with an existing dispatch. `approve_request` binds an owner confirmation to scope, dispatch, revision and expiry (maximum one hour). It does not allow a denied requester. The same requester remains responsible for every model/tool-loop invocation.
7. Before executing a high-risk tool, build `ToolProposal` with exact arguments, canonical working directory, tool name, risk, dispatch, scope, the three current policy revisions and expiry. `authorize_tool` intersects initial and current three-layer policies. `AskOwner` requires `approve_tool`; it binds every proposal field and is single use. Parameter, requester, thread or policy changes invalidate it. Exact directory allow rules are deliberately conservative; the runtime must resolve symlinks safely and intercept the actual subprocess operation.
8. `ModelProfile` stores a `keychain:` reference and local workspace metadata only. Resolve the reference in the trusted host via an OS credential store. Do not transmit that secret or this ledger to the server.

The ledger does not provide a login UI, quota UI, Keychain implementation, device lease coordination, provider adapter, encrypted export; missing usage is settled automatically as zero. Those belong to the surrounding client integration. Tests here cover real concurrent SQLite connections, crash/reopen recovery, budget periods, wrong owner/scope, policy widening, changed tool parameters and repeated settlement. They do not constitute an end-to-end Codex/Palpo validation.

## Codex app-server adapter

`codex::Profile` requires canonical executable, local OS home, dedicated owner-only `CODEX_HOME` and an explicitly selected workspace. The owner initializes provider login in that dedicated directory; the adapter never reads/copies `auth.json` or overwrites existing configuration. A `config.toml` in the dedicated login home or `.codex/config.toml` in workspace ancestry is rejected. The child receives only HOME/CODEX_HOME/PATH. Server, Matrix and device tokens are absent.

The default chat profile disables native shell, file execution, MCP, hooks, plugins, subagents and skill loading. The separate owner-selected programming mode enables native commands and file changes plus explicitly configured MCP servers. Programming uses the Agent's selected workspace, shared by its Rooms; it does not claim operating-system filesystem confidentiality between Rooms. Provider and Matrix credentials are not exposed as model tools.

Programming children use the platform guardian or Windows job from startup. A canceled initializer retains process-tree custody; a completed or canceled turn must obtain a whole-tree stop observation. `enable_programming` requires a host-only current-execution gate. The production gate checks the exact Pasion owner/device, lease, Room/requester/thread, dispatch body/generation and original running execution before a turn or native approval, and again after an owner wait.

Drive `initialize()`, `open_context(ledger, verified_scope, profile)`, then `run(...)`. Opening a context validates the real thread ID, working directory, model, `untrusted` approval policy, `user` reviewer and read-only/no-network sandbox. Scope is pinned to the opened context; the session rejects a different Room/requester/thread. The desktop host must serialize turns in a context and stop/drop `Process` on revoked device authorization or lost lease. Killing the app-server child does not prove that every previously approved descendant has stopped.

`BudgetMode::default()` is `Strict`, which returns `StrictQuotaUnsupported` before `turn/start`. The installed 0.160 `TurnStartParams` schema has no enforceable output token maximum or model-call-before-hook. `Estimated { reservation }` is an estimate for an entire turn, including hidden tool-loop model invocations. It does not satisfy a strict upper token-cost guarantee. Known cumulative input/output usage increments are settled with the context baseline in one transaction; cached/reasoning counters are subsets. Failed turns with known usage are charged. Missing or lost usage is recorded as zero. Known actual consumption beyond an estimate is charged normally; only configured budget limits govern subsequent work. Missing cumulative baselines are marked independently while retaining conversation context, so a later cumulative total cannot charge the old missing turn as new work.

The default chat profile declines native execution callbacks. Programming routes exact command, file-change and configured MCP tool proposals through the same owner queue and three policy layers. It returns only one-operation acceptance; it does not grant session-wide command or network rules. `approval_queue(capacity)` returns a trusted host queue and receiver. Callbacks are associated with active thread/turn/item facts; full arguments and three policy revisions bind confirmation. The UI displays a `PendingApproval` and calls `decide` after checking the current owner session. Explicit deny never enters the confirmation queue. Queue expiry, changed policy, uncertain charge or a disconnected UI denies the callback. This queue must stay inside the trusted host; never expose it as an unauthenticated model tool.

The source protocol was checked against `codex-cli 0.160.1 app-server generate-json-schema --experimental`. An inference-free runnable smoke test is available:

```sh
cargo run -p hagency-agent-local --example codex_handshake -- /absolute/path/to/codex
```

It starts the actual local process in disposable fresh state, initializes the protocol, opens a scoped read-only thread, and stops it. It does not start a model turn, execute a tool, or prove model-account entitlement. Official protocol reference: https://learn.chatgpt.com/docs/app-server .

## Durable local inbox contract

The `inbox::Dispatch` serde shape matches the new server transport envelope. The trusted device transport verifies its owner/device/Agent lease and fetches the owner-scoped binding before passing the envelope to this crate. The envelope cannot authenticate its own owner. `Dispatch::scope()` uses the real requester MXID and Room/thread identifiers.

1. `receive_dispatch(owner, event, limits, now_seconds)` validates the registered local binding and permanently records immutable event/scope/body/binding-generation identity, returning a `Receipt`. **Only after this returns successfully may the host send server ACK.** Changed payload with the same dispatch ID, or another dispatch ID for the same binding/event, conflicts. Capacity rejection returns no receipt. Record capacity counts active records; byte capacity includes retained envelope/reply UTF-8 payload and a conservative proof allowance for every record, including terminal deduplication receipts. SQLite page/index/WAL overhead is separate.
2. After an acknowledged server ACK, call `acknowledge_dispatch`. A lost ACK response can be retried using the same durable event. Delivery epoch/device may advance while an event is received/acknowledged; late older delivery cannot overwrite a newer epoch. Once prepared, lease metadata is frozen.
3. `prepare_execution` requires acknowledged state and writes a stable random execution ID **before** posting server start. Repeated calls while prepared return the same ID. `confirm_execution_start(owner, ServerStart)` validates the complete response identity, binding generation, execution ID, epoch and device. Only `newlyStarted=true` plus local prepared state returns a non-cloneable `RunPermit`. Concurrent confirmation readers yield exactly one permit. `newlyStarted=false` never starts a model; a prepared record becomes unknown. Repeated true responses in running state also return no permit.
4. Consume the permit into its `Prepared` descriptor, use that stable execution ID as the Codex turn call ID, and its original dispatch/requester scope for every model/tool action. The host must keep execution identity separate from thread/model-session identity.
5. Before sending a server reply, call `persist_execution_reply`. The reply becomes durable `reply_ready` and has immutable digest/content. On a lost HTTP result, retry that same execution/reply, never another model turn. `confirm_matrix_delivery` may be invoked only after the host verifies a scoped `sent` receipt with a Matrix event ID. Server outbox acceptance keeps `reply_ready`; it can later need reconciliation after lease expiry. After this trusted sent proof, the terminal receipt retains identity, immutable original digest, execution and reply digest while clearing duplicated plaintext. Exact redelivery cannot mint a new execution and changed content still conflicts. Unknown execution identities remain permanent; terminal request bodies with settled or absent usage may be compacted. Missing local historical receipts count as zero; server execution custody prevents replay and every available local accounting proof is still validated. Unsent known replies retain their original text. A changed reply conflicts. `inbox_by_state(ReplyReady)` supports outgoing retries independently of interrupted records.
6. `finish_local_execution` records rejected, failed or unknown dispositions; it does not fabricate zero usage or release model reservations. Send the matching server finish request separately. On an exclusive device restart, `recover_local_executions` atomically seals local prepared/running work as unknown and settles pending provider estimates as zero. Received/acknowledged requests and already durable replies survive for ACK/dispatch/reply reconciliation. Unknown cannot transition back to running.
7. Use the circular `inbox_for_binding_after` recovery scan to bound historical retries and leave new polling free to progress; `inbox_pending` is a bounded combined reconciliation view. Preflight `inbox_available_bytes` before model work and handle a full reply store by retaining the known result for owner recovery, never regenerating it. The byte preflight is a snapshot rather than a capacity reservation; concurrent new events can still exhaust capacity. The host exposes `inbox_capacity` for active/terminal receipt counts and charged bytes. Permanent metadata still consumes storage; this is not unlimited historical retention or secure disk erasure.

The pure library implements no network polling, device authorization refresh, lease heartbeat, event expiry policy, retention cleanup or external secret store. These operations belong to the authenticated trusted host. No old Fleet/Engagement data or sessions are imported. Tests use real SQLite connections and process-like reopen/recovery to verify ACK durability, one concurrent execution permit, unknown no-replay, immutable reply retries, wrong owner/scope/lease, and payload capacity.

The new trusted desktop host lives in `crates/hagency/src/console/owned_runtime.rs`. It uses an explicit owner start and estimate selection, fresh authenticated device operations, a per-Agent lease heartbeat and scoped recovery. Provider credentials use Codex's own OS keyring entry keyed by the canonical dedicated `CODEX_HOME`; `Profile::spawn` forces `cli_auth_credentials_store="keyring"` without file fallback. The host verifies the credential locator against its exact owner-specific directory and then requires `account/read` to report an account before announcing chat availability. A locator is not itself proof of login, and account presence does not guarantee a future provider request will succeed. No credential values are read by this library.

`recover_agent_executions` is the restart operation for one independently leased Agent; it preserves other Agents' active calls. `inbox_for_agent` selects bounded work for that Agent so another Agent's backlog cannot starve it. The host stops provider execution on cancellation or loss of authorization/lease. Durable original replies retry transport failures while the original lease is still usable. Cross-epoch known-reply reconciliation uses the separate server endpoint with the original immutable execution/body/binding generation/epoch and the current owner/device lease. An accepted but unsent reply remains `reply_ready`; it is terminal only after a scoped Matrix `sent` proof. Unknown executions never run their model again.

## Scoped host dynamic files and owner approvals

`Session::enable_host_files(Workspace, Arc<dyn HostToolGate>)` is a trusted host attachment before opening the provider context. It advertises only `hagency_file_list`, `hagency_file_read`, and `hagency_file_create` through the installed 0.160 dynamic-tool protocol. Model arguments cannot select a root, credential or create nonce. `Workspace` holds a binding-specific root FD beneath the verified owner directory; the host process cwd uses that generated root. Native shell, file/image, web search, MCP, hooks, plugins, app and subagent capabilities remain disabled. Host files do not imply an unrestricted native OS sandbox qualification; replacement is unsupported.

Every `item/tool/call` is pinned to its exact Codex thread/turn/call and the Matrix owner/Agent/binding/Room/requester/thread context. `HostToolGate` must obtain fresh server authorization for the original running dispatch/execution before IO, and again after any owner wait. `Workspace::prepare` binds arguments, root, three policy revisions and expiry into the proposal. `Workspace::execute` consumes the precise local permit itself. Deny never reaches an approval prompt; exact allow-rules can authorize automatically; AskOwner parks the original proposal in the owner host queue. A repeated call with changed arguments is rejected. A proved creation receipt can return the original result without creating or consuming another permit; an unproved publication seals uncertainty instead of blindly replaying.

`OwnedRuntime::pending/decide` exposes opaque random proposal IDs and a digest of the complete original proposal. The host verifies owner cookie, current Pasion subject/device/generation, Agent and active binding before consuming the one-time decision. The adapter then rechecks remote scope and local revisions. Model requests use the same UI queue with `tool="model.request"` and `risk="model_request"`, but authorize with `Ledger::approve_request_exact`, not a high-risk tool permit. Changing request parameters, requester, Room, policy revision or execution cannot reuse a confirmation.

Tool-enabled provider contexts and usage baselines use the separate `hagency-room-files-v1` key; existing chat histories are retained. The adapter explicitly selects Codex's JSONL history mode (`historyMode="legacy"`, unrelated to historical Hagency data), materializes a fresh thread by its metadata update, and verifies the same scope on resume. If the provider explicitly confirms that this exact stored thread no longer exists, a new thread serves the current new request and starts its own cumulative baseline; historical charges and executions remain unchanged. Arbitrary resume errors never clear context or accounting. Process-local config forces zero project-document bytes, no bundled/automatic skill instructions, empty developer instructions and disabled native features. `config/read` verifies those effective settings; dedicated global `AGENTS.md`, overrides and skill directories are refused.

The inference-free `codex_host_files_handshake` example validates real installed dynamic-tool registration, independent context creation, effective config, and cross-process resume without model or file-tool calls. Fake protocol tests exercise actual host file effects, denial and revocation during owner approval, duplicate/changed calls and real usage settlement. Strict provider token caps remain unavailable; explicit estimate mode can still overshoot and records unreported usage as zero without blocking later work.

## Initialization and terminal inbox retention

Fresh schema detection runs after acquiring SQLite's immediate transaction lock, so concurrent first openers reuse the committed schema and its permanent owner/profile identity. Rejected requests with an exact no-provider-call proof, and failed/interrupted requests with an exact settled usage/scope/snapshot/account proof, compact their request body without deleting execution IDs, immutable digests, call settlements or budget balances. These compact terminal receipts do not consume active record slots; their retained metadata still consumes the byte limit. Interrupted records never consume active work slots. Unsent original replies retain their full payload and active slot; failed records without a settlement proof retain their payload. Missing usage receipts count as zero in continuity checks; execution scope and any available accounting proofs are still validated.

## Programming configuration

`ModelProfile.programming` defaults to disabled on schema upgrade. Enable it in **Model & resources** on the execution device, save the model and restart the Agent service. Configure the Agent, Room and requester high-risk policies to ask the owner or to allow exact tool/directory rules; a deny at any layer still denies the operation.

MCP settings use an explicit JSON object, for example:

```json
{
  "docs": {"transport": "http", "url": "https://example.test/mcp"},
  "local": {"transport": "stdio", "command": "/absolute/canonical/server", "args": []}
}
```

Stdio executables must be existing canonical absolute files. HTTP supports HTTPS and loopback HTTP. Each server uses per-tool prompting; ambient Codex servers, environment injection, hooks and plugins remain disabled. Programming refuses an existing Codex `rules` directory or workspace-ancestor `.codex/rules` directory so inherited prefix approvals cannot bypass the owner policy; use a separate Codex sign-in when the everyday account has such rules. The v1 remote configuration transport excludes programming/MCP settings and preserves them when remotely editing ordinary Codex model settings. Configure these capabilities directly on the execution device.

Programming contexts and cumulative accounting baselines are separate from chat and restricted host-file contexts. Their identity includes saved programming/MCP configuration, workspace, model, reasoning and web-search choice. Missing usage preserves conversation history while fencing the old cumulative baseline; unknown executions never replay.

The inference-free `codex_programming_handshake` example exercises the installed CLI, an actual fixture MCP server, context resume and whole-tree stop. Passing an existing canonical Codex login directory as a second argument additionally invokes a real model in a disposable workspace, checks exact existing-file edits, command output and MCP effects, and requires exact fixture-owner tool decisions. It uses provider-owned login without copying credentials.
