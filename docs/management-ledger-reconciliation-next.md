# Explicit reconciliation of profile ledgers into the owner registry

Date: 2026-10-16. Status: read-only audit slice implemented; migration protocol below remains a proposal. No live profile has been migrated. The owner registry, provider identity observer and parent settlement writer are additive foundations; none makes an existing profile's resources safe to allocate through the new registry automatically.

Companions: `docs/management-allocation-native-next.md` and the server's `docs/design/hagency-parent-grant-settlement-next.md`. This proposal preserves the current project request/admission flow and keeps reservation capabilities unavailable until reconciliation and the production adapters pass their acceptance tests.

## What actually needs reconciliation

The current native host has two distinct databases per authenticated profile:

| Source | Current responsibility | Migration constraint |
| --- | --- | --- |
| `owned-agent-owners/management_<profile>/domain.sqlite3` | Resource definitions, the legacy resource/seat/engagement ledger, local management intents and exact command receipts | Preserve every commitment and receipt. Profile-private sessions rely on selecting this database for isolation. |
| `owned-agent-owners/owner_<profile>/agent-local.sqlite` | Personal-agent reservations, calls, usage, bindings, approvals and runtime metadata | Preserve human/device ownership and unknown execution. Do not import credential references or workspace paths into public results. |

`console/owned_agents.rs::profile_identity` binds origin, issuer namespace, authenticated subject and owner. `NativeOwner::management` opens the first database with `DomainRepository::open_managed`. Its durable `management_identity` rejects another profile. By contrast, `management::Session` resource methods assume that database isolation; they are not a shared-registry ACL. Redirecting `NativeManagement.store` to the owner registry would expose other profiles' resources and break private command custody.

The resource connection's old `seat_embedded_*` identity includes Matrix owner, runtime and provider locator. Different profiles can therefore contain different seats backed by the same actual provider subscription. The new verified account identity deliberately excludes these fields. Only an authenticated provider observation plus explicit owner linking can establish that two old seats belong to the same account. Different filesystem paths do not prove independent capacity.

The personal ledger introduces an additional trap. `recover_interrupted` can settle an unreported call with accounting version `unreported-zero-v1` and record a usage-gap marker. A numeric balance of zero is therefore not proof that no work ran or that no liability remains. Any such history requires conservative reconciliation, even if no row currently has a positive hold. Calling normal personal-ledger startup during an audit would change precisely the evidence being inspected.

## Inventory must not run startup recovery

`DomainRepository::open_for_migration` skips execution recovery but still calls `database::open`: it creates or opens the lock, upgrades the schema, opens a writable SQLite connection, configures WAL and initializes the account registry. It is not a read-only inventory API. `Ledger::open_scoped` likewise creates/updates schema and identity.

The first audit should run pure queries through an already-owned `DomainStore` worker. That sees committed WAL content and provides a bounded queue without a second writer. It must not call recovery, open provider credentials, create a new profile or change pragmas. Its result is a current observation, not a durable migration plan or a promise that the source will stay unchanged.

Offline inventory needs a separate implementation. It must validate private files and physical directory identity, hold the original ownership locks and read the real WAL snapshot. SQLite `immutable=1` is unacceptable for a possibly live WAL database because it can omit committed frames. Opening a read-only WAL connection may still touch shared-memory read marks, so tests and documentation must distinguish no durable database change from an unsupported byte-for-byte promise about WAL shared memory.

Native profile discovery should use host-projected account metadata and registered app roots, never expose full login bindings. There is currently no installation-wide census of independent app data roots. The owner must review the source set and explicitly identify additional installations. A scan of one root cannot establish that another root or an old backup has no liabilities. Unregistered/downlevel copies remain a migration limitation; a new process cannot fence arbitrary old binaries and copied databases merely by creating a new registry file.

## Required invariants

1. One provider quota account has one owner-controlled declaration and one authoritative accounting writer. Old ceilings are never added together. Resource-level ceilings remain subordinate limits, not additional provider capacity.
2. Every existing, consumed, reserved, uncertain or unreported liability remains charged or blocks activation. Unknown tables, accounting modes and receipt conflicts fail closed. Historical zero does not imply an unused account.
3. Keep original resource IDs and revisions when their complete canonical meaning is preserved. Otherwise require an explicit resource amendment; do not disguise a changed account binding as an unchanged definition.
4. Private intents remain bound to the original Matrix profile, owner and installation. Shared resource access requires an explicit profile ACL. Copying a capacity commitment does not transfer provider credentials, private conversation history or workspace access.
5. Source allocation is durably fenced before destination allocation becomes active. A crash may leave both sides unavailable or retain a conservative duplicate hold. It must never make capacity available on both sides.
6. Original command IDs, digests, immutable effect receipts and uncertain outcomes survive migration. A lost response is recovered using the original operation, never a fresh command that silently repeats it.
7. A current provider proof is necessary but not sufficient. Future execution must still verify that its runtime uses that account; unmanaged external provider use is outside the local allocation guarantee.

## Can existing resource identity be preserved?

`Resource::id()` hashes only `presetId`. `resource_publication_revision` hashes the whole normalized Resource, including `seatId`. Keeping a preset while replacing its seat preserves the public resource ID but changes its revision.

For the first compatible source, identity-preserving adoption is possible: retain the original Seat and exact Resource JSON, and bind the verified provider-account digest to that existing seat in the private owner account mapping. Subsequent enrollment must resolve that mapping before deriving a new `seat_owner_*` ID. This requires a reviewed declaration and proven reconciliation; it is not permission to trust the old seat's path as identity. It also requires the destination to have no conflicting provider mapping or same-ID definition.

When two source profiles use different seats for the same provider account, simple copying is insufficient. Two options are explicit:

- Rewrite one resource's seat to the chosen account seat, keep its preset/resource ID, and publish a supported central amendment with the changed revision after fencing the source. Do not replace a live contribution by inventing a new contribution or legacy registration.
- Preserve both exact resource definitions using private seat aliases that resolve to one account declaration. Every existing budget, usage, coordinator and parent-grant path must aggregate those aliases consistently. This is a larger accounting change and is outside the first migration slice.

Do not select the alias option merely to avoid a UI amendment. If any commitment calculator still uses the old seat independently, capacity can be counted twice. Current same-ledger conservation tests are necessary but do not establish cross-ledger reconciliation.

## Keep private journals and authoritative effects separate

`management_commands` and `management_intents` are keyed by actor scope and command ID. Actor scope hashes owner plus device; profile isolation currently comes from the containing database. Importing these rows unchanged into one shared table can collide across authenticated subjects/origins and expose another profile's history.

The source's private journal should remain archived/private with its exact original scope and payload. The destination needs an explicit enclosing source/profile provenance for imported effect receipts. An authoritative capacity mutation and its exact result receipt must be committed in the same destination transaction. The private intent may record progress before and after that transaction and recover the exact destination result; it cannot pretend that two separate SQLite databases share a transaction.

Pending intents without a result remain unresolved. The migration must recover the original effect or stop at an inspection-required state. Existing central project intent recovery must continue to return the latest project projection without issuing another mutation. A source archive is not disposable after activation: immutable receipts and historical liabilities remain evidence for reconciliation and cleanup.

## Proposed native protocol

All constructors are native-only. Splash can request an audit and display its safe projection; it cannot supply a path, provider subject, source fence or `approved: true`.

1. **Audit.** A trusted host captures authenticated profile context, the current owned writer, physical source identity and a bounded inventory. Report table/category counts, safe resource IDs/revisions and explicit blockers. Provider identities, credential references, raw journals and filesystem paths stay private. Include a separate completeness status for personal-ledger history and the owner-reviewed source census.
2. **Prepare.** After the owner chooses the account mapping and declaration, create a canonical migration plan bound to source identities, exact inventory digests, current verified provider proof, destination registry identity and all requested ACLs. A non-serializable, expiring, single-use `OwnerMigrationConsent` binds that exact plan. Recheck it after queue waits.
3. **Quiesce.** Retire source package/resource authorities and drain personal and shared runtimes. `DomainStore::shutdown` must definitively close the original connection and release its writer lock. A timeout/`OutcomeUnknown` is not proof of closure. Reacquire and retain the same source ownership locks; repeat the inventory and reject a changed plan.
4. **Fence.** Durably write an irreversible source migration identity before destination activation. The original `DomainRepository::open` must refuse it even after restart. An applicable personal ledger needs its own durable fence: `Ledger::open` also verifies its application identity, but it has no equivalent standalone process lock, so the trusted host's retained root ownership and runtime shutdown are required. Fencing only the domain database would leave the personal execution path able to spend from the old provider independently. A separate archive/journal reader may serve historical receipts. The proposed fence is an explicit archive application identity plus a private manifest bound to destination registry and source physical identity, not a fabricated future schema version or fake legacy registration. Its exact format still needs an implementation review.
5. **Import provisionally.** In one destination transaction import the approved definitions, retained liabilities, exact effect receipt provenance and explicit profile grants. Record the migration digest and original source fence proof. Keep the imported resource unavailable until the complete plan is satisfied. Unknown history is retained or remains quarantined; it is never converted to an empty account.
6. **Activate and redirect.** Publish a durable source-to-destination mapping and activate only after every source is fenced and every imported liability is verified. Native services use the owner registry ACL for resource effects and the private archive for journal custody. Personal execution must use a shared account admission/charge adapter or remain unavailable for this migrated provider.
7. **Recover.** Resume the same migration ID through `prepared → source_fenced → destination_imported → source_redirected → active`. Before a source fence, cancellation can discard an uncommitted plan. After a destination import, recovery must reconcile the original records; it must never simply re-enable the source. A central publication failure retains the native hold and original receipt for retry, without a replacement native grant.

The migration journal belongs to the canonical owner registry. Source manifests provide the durable refusal boundary and redirection evidence. Copies of a source require their own explicit treatment; merely preserving an inode/path in a manifest does not fence a separately copied old database.

## Smallest implementation slice

A **read-only profile-ledger audit** is implemented on the already-owned store, behind native host context and existing resource-read permission. No migration operation, schema change, new enrollment capability, source opener or shared resource redirection is included. The result always says that provider mapping, personal-ledger history and installation source discovery are not yet established by this audit.

`NativeManagement::reconciliation_audit()` derives the profile digest from the current authenticated native device and delegates to `management::Session::reconciliation_audit`. The session checks exact host context and `ReadResources` before queueing, inside the worker, and before returning. `domain/reconciliation.rs` requires the existing `management_identity` and exact supported schema, then opens a deferred query snapshot on the same connection. It does not open another ledger or rerun recovery. The safe `ProfileLedgerAudit` projection contains `adoption: not_assessed`, counts, original resource IDs/revisions and blockers, with no paths, provider identifiers, raw command payloads or table names.

Queries cap table discovery at 256, per-table row counts at 10,000 and resource projections at 64. Capped observations are explicit lower bounds and add an observation-limit blocker. Resource configuration parsing has a separate 16 KiB bound. A populated unclassified table remains blocking history. These limits bound this inspection; they do not certify an entire historical migration or provide a digest suitable for future activation.

The audit should classify current source tables conservatively into definitions, private command custody, resource/usage/execution history and other populated history. An unrecognized populated table blocks a simple adoption. Resource rows are projected as existing ID/revision only; command rows are counted by state and no payloads are returned. This creates concrete evidence for the owner flow without prematurely making allocation safe.

Seven focused synthetic tests pass for authenticated profile/permission mismatch, retirement while queued, row/schema and main-file/WAL bytes unchanged during the query, visibility of existing WAL commits, pending command and populated unknown history, bounded output and exact resource ID/revision preservation. A retained legacy allocation with a started execution remains unchanged; inspection does not run startup recovery. No real profile was opened for these tests. This source-level test coverage does not validate the separate personal-ledger audit, source census or migration protocol.

A following implementation can support only a strictly proven definition-only source with no personal execution or unknown history, while retaining all private receipts. A populated historical ledger requires a separately reviewed importer for its complete related graph and cleanup/usage semantics; a generic table copier is not that importer. Parent settlement's conservative unknown accounting mode remains intact.

## Activation acceptance

- Fault-inject every migration phase, including loss of replies after each commit. Reopening old/current binaries must not allocate from a fenced source; restarting migration must recover the original destination result without duplicate holds.
- Test two profiles on different homeservers and two app roots using the same provider account, including different runtime/model/provider paths. Reject conflicting mappings and never sum independent declarations.
- Preserve existing resource ID/revision in the compatible case; require and recover an explicit revision amendment in the incompatible case. No fabricated registration, room or Matrix project may satisfy a legacy foreign key.
- Verify legacy engagement/coordinator holds, consumed usage, unknown calls, unreported-zero history, old receipt identities and conflicting/pending operations. No rollback or cleanup may free uncertain liabilities.
- Verify current package/profile expiry, denied ACL access, native consent rejection, changing provider identity, source mutation after audit and a missing source ledger. Every case leaves allocation unavailable rather than inferring empty capacity.
- Verify private journals remain scoped and recovered after redirection. Neither mini-app output nor logs contain provider identifiers, credentials, raw receipts, workspace paths or private message contents.

Until these pass through the real native host adapters, the audit and the new owner ledger remain preparation work, not a completed migration or an end-to-end resource allocation claim.

## Concrete next production slice: inspect existing sources, then adopt definitions

The first production adoption should handle the data already produced by the current contribution flow: exact Seat/Resource definitions, completed resource command receipts, and completed central admission/project intents. It must not require deleting those records, making a fresh synthetic resource, or issuing a replacement contribution. Existing capacity/execution history is a separate, blocking branch until its importer is implemented.

The source layout is now concrete. Desktop derives its owner root from `app_data_dir()/native-owner/<hash(origin, owner)>`; native profile directories beneath that root additionally bind issuer and authenticated subject. `server-login-profiles.json` is descriptive account metadata, not authorization. `OwnerHost::State` retains the root's `.owner-client.lock`. The current host can reuse that ownership handle; another root must be inspected only after acquiring its existing lock without creating a root, lock, marker or database. A busy or unknown root is an explicit incomplete observation, never silently skipped.

### Slice A: bounded source census and existing-file audit

This boundary is implemented as read-only native source inspection, before any source mutation:

- The trusted host constructs a non-deserializable `SourceInspectionRequest` bound to one exact `NativeOwner`, its reviewed `ReadResources` package/instance/account epoch, a live native callback, a deadline of at most 30 seconds, and up to seven explicitly selected additional existing roots. `NativeOwner::inspect_reconciliation_sources` adds the current root without constructing `NativeManagement`. Production callers cannot substitute an environment variable, mini-app path, guessed profile hash or provider-home path. Track physical root identity as well as its locator. Validate every existing ancestor/directory/file against private ownership, symlinks and replacement; the current file helpers that create directories are not an audit opener.
- Derive the current profile from the actual SDK-authorized device. Within each admitted root, compare the saved descriptive profile census with the existing `management_<digest>` and `owner_<digest>` directories. Extra directories, missing/corrupt markers, duplicate physical databases, unreadable roots or unsupported formats remain blockers. A current Matrix profile receives only its own detail projection. Cross-profile source selection requires a separate native OS-owner review; it does not grant one Matrix user access to another profile's journals.
- The existing owned DomainStore audit remains available to an already-open management session. This independent census uses existing-file-only read-only connections and shares that collector through `DomainRepository::audit_readonly_connection`; it never constructs a repository or calls `open_for_migration`. The personal inspector shares its original collector through `reconciliation::audit_readonly_connection`, without `ledger_path`, `Ledger::open` or `open_scoped`. The latter currently create the file, bind identity, add columns and update markers.
- An inspection queue has a fixed small capacity, a bounded SQLite busy timeout and a finite current-native-authority gate before queueing, in the worker and before returning. Use `SQLITE_OPEN_READ_ONLY` and one deferred snapshot, with exact application/schema/profile checks. No DDL, recovery, account initialization, journal-mode change, checkpoint or `immutable=1`. Validate main/WAL file identity around the snapshot; WAL shared-memory read marks may change, but main/WAL data and every recorded liability must not.
- Distinguish `not_present`, `inspected`, `busy`, `unsupported`, `unreadable`, `changed`, `recovery_required` and `observation_limit`. An absent personal file is not a certificate of an unused provider: correlate the profile directory, runtime-intent metadata and source census. A malformed or partially initialized directory remains blocking. All audit projections continue to state `adoption: not_assessed`.
- Return counts, exact public resource IDs/revisions and named blockers. Retain source handles and private provider/configuration evidence inside the native host. Do not return filesystem paths, issuer subjects, provider account IDs, raw command payloads, credential references or workspace information to the mini-app.

This slice makes the real owner fixture inspectable without changing its resources or receipts. Its acceptance test uses populated synthetic source definitions plus completed admission receipts, a committed WAL update, an unreported-zero personal call, an unknown table, an inactive second profile and a second process holding the root lock. Main/WAL bytes and row states must remain unchanged. No operation may create a missing personal ledger merely to report it empty. Retirement while queued must suppress the result. It deliberately does not advertise allocation support.

The native inspection checks the current SDK source and exact device/profile/generation before and after the bounded job. It deliberately does not call native `sync_matrix`/`renew_matrix`; the SDK retains its own refresh policy. The two-job queue retains its permit and owner/root handle until a canceled read finishes or observes its expired gate. Every SQLite query uses a deferred read snapshot, a 100 ms busy timeout and a progress handler tied to the finite gate. The pinned SQLite VFS also receives `readonly_shm=1` through a library-encoded file URI, so a missing shared-memory companion is not created by its opener. A WAL-mode source lacking either existing WAL or SHM is reported as requiring recovery rather than allowing inspection to create a companion. Existing SHM read marks are not compared byte-for-byte.

Previously supported source schemas 71–77 are inspected without migration after their required ordinary tables/columns and exact identity are checked. Missing later history tables are projected separately and add an older-schema blocker. Unknown schema versions remain unsupported until their additive changes and fixtures are reviewed. Completed resource-admission receipts do not themselves disqualify a source; pending/unknown history remains visible and blocking.

Inspection is a per-database observation, not a cross-database import snapshot. The current owner's already-running configuration/runtime work may initialize or modify sources independently; tests distinguish that concurrent legacy activity from inspection's own writes. The source collector never opens a second NativeOwner for a selected external root. Cooperative locks and checks around a path-based SQLite connection are not an ABA-proof import primitive against arbitrary same-OS-owner processes. All results retain `adoption: not_assessed`, an incomplete external-census flag, and old-writer/provider/migration blockers. Source fencing, immutable inventory digests and actual transfer remain Slice B work.

### Slice B: adopt that inspected source without changing its public identity

After Slice A identifies an eligible source, the smallest complete transfer is a native owner-reviewed, resumable **definitions-and-private-custody** adoption:

1. Require the complete source census and a fresh authenticated provider identity. The destination must have no conflicting verified-account mapping. Retain the exact source Seat ID/declaration and complete Resource JSON; map the provider digest to that existing seat instead of generating `seat_owner_*`. Select one owner declaration, never add ceilings from different profiles. If another source uses a different seat for that provider, stop for an explicit amendment plan; do not silently alias it.
2. Require no legacy resource, project, agent, execution, usage, uncertain effect or parent/child allocation history. Validate private command operations against the supported completed-operation set. A pending or unrecovered command is resolved through its original identity first. Completed admission/project receipts remain admissible private custody; they are not zeroed or copied into another profile's journal. Source definitions are immutable for the duration of the plan.
3. Persist the exact plan and phase journal in the canonical owner registry under one original migration ID. The plan binds source physical identities, profile digests, canonical definitions, private-custody inventory digest, provider identity proof, original central resource revision and explicit destination profile ACL. Expiring single-use native owner consent approves this exact plan; source changes invalidate it.
4. Quiesce the old native resource authorities and personal runtime starts, drain all runtime/provider work, and close the domain writer with a definitive shutdown acknowledgement. Retain the OwnerHost root lock throughout. Reacquire the original domain ownership lock and re-audit under those locks. Timeout, an uncertain writer shutdown, a still-running binding or changed inventory stops the transfer before activation.
5. Write the source refusal fence durably before any destination resource becomes usable. Use a dedicated archive application identity plus a versioned manifest bound to this migration and destination, verified by every new opener. Existing normal domain and personal openers already reject an unfamiliar application identity. For an absent personal ledger, create an explicitly marked archive-only refusal sentinel with the archive application identity and a private manifest; it is not an initialized personal ledger and contains no fabricated legacy records. A manifest alone is insufficient because downlevel `ledger_path` ignores unfamiliar sidecar files when the normal profile marker exists. Current openers must also check the manifest before any create operation; tests must show the old Ledger opener rejects the sentinel. Do not claim that a root marker fences an arbitrary already-running or copied downlevel binary; every selected original writer must have been drained, and unknown copies remain outside the proven census.
6. Import definitions, the verified-account-to-original-seat mapping and narrowly scoped resource ACLs in one destination transaction; save the exact import receipt in that transaction. The source's private journals remain at their original location. Add a separate typed journal-only archive service for their existing recover/list/acknowledge operations. It must accept only the explicit archive identity and exact original profile, and cannot expose resource/execution mutations. Redirecting all of NativeManagement to the shared ledger is expressly excluded.
7. Only after every source fence/import receipt matches, activate the destination mapping. Existing central contribution ID/resource ID/resource revision remain unchanged in the compatible case. Native grant publication then uses the existing accepted contribution and original publication-recovery rules. Personal execution stays fenced until its account-bound shared-ledger admission/charge adapter exists; a successful resource adoption is not permission to resume the old personal writer.

Recovery resumes `prepared → sources_fenced → imported → private_custody_ready → active` using the same IDs and digests. After a source fence, cancellation cannot restore its allocation authority. A crash between source and destination commits may leave capacity unavailable, but never available twice. A post-import lost reply recovers the original import receipt. A central publication rejection does not undo the imported resource or refund an existing native hold.

Before implementing Slice B, prove the archive reader and absence fence against old/current openers, inject a crash at each boundary, and recover existing admission receipts from the original private journal after resource redirection. Two different source profiles for one physical provider must either converge on one explicitly reviewed account declaration or remain blocked; the implementation may never turn incomplete discovery into two independent budgets.

A concrete archive-custody dependency identified during the managed setup review has now been extracted: configuration journals and both `matrix_creations::service::Scope::new` and `Scope::management` use `owned_agents::journal_profile_directory`, which validates the original profile namespace without opening the personal database or rewriting a supported legacy marker. The actual personal `ledger_path` still validates the database before allowing personal operations. This preserves the original Matrix/configuration journal paths when a future personal-ledger refusal fence is installed. The journal path itself grants no database or allocation authority. Slice A does not call either path helper during inspection.

The final Slice A checkpoint passed 15 native census tests, 11 domain reconciliation tests, 8 personal audit tests and strict `cargo clippy -p hagency --lib --tests -- -D warnings`. Schemas 75 and 76's additive managed-agent/custody tables and retention triggers were reviewed; populated histories remain blockers, not imported effects. The concrete next implementation boundary, adapter changes, source refusal sentinel and crash phases are specified in `management-ledger-adoption-checkpoint.md`. That proposal remains unimplemented.


### Schema 77 compatibility review

The additive `owner_managed_fences` table was reviewed after its real 76→77 rollback/reopen test passed. Read-only audit now requires the ordinary table and its original-command, semantic identity, project, device and fence-revision columns whenever the source claims schema 77. Missing or renamed required columns reject that claim. Its immutable semantic tombstones are counted as retained other history; they never qualify a source as empty or authorize new capacity. Older schema fixtures explicitly omit this table, retain their original schema and report the missing later history separately. The private journal archive accepts the same reviewed source version without gaining any fence or resource operation.
