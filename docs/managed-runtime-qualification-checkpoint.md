# Managed runtime qualification and retained cleanup

This checkpoint connects central schema 11 commands to canonical owner-ledger schema 79 and one retained Codex supervisor. It authorizes metadata-only qualification followed by stop. It does not authorize prompts, model turns, tools, Matrix replies, usage settlement, successor assignments, or capacity release. The native `managed-runtime` Cargo feature defaults off; no Desktop route or package capability enables it. The central runtime flag also remains off.

## Exact custody and transport

`ManagedRuntimeTransport` uses the existing native SDK/profile/device authorization, the original enrolled installation and current canonical reservation. Fresh provision checks the original generation. Historical recover never creates custody. Cleanup may use a newer generation from the same enrolled installation, preserving the original command, assignment, reserve receipt, and child identity.

The schema 11 provision/stop commands and canonical fixtures remain unchanged. Each upload uses a bounded original delivery ticket. The native command deadline is pinned to `Instant` once, including the command's remaining wall-clock lifetime and the enrollment and transport bounds. A new HTTP response or a wall-clock rollback cannot extend that authority. The maximum 30-second command is a temporary qualification lease, not persistent agent readiness.

A fresh stop may carry a previous unknown observation and still permit cleanup. The adapter accepts that specific shape, inspects the exact retained task and canonical history, and uploads the native result. It never interprets a missing in-memory manager entry as a stopped or never-started process. Original qualified observations remain recoverable after a later local stop; they describe the original observation, not fresh execution authority.

## Retained process lifecycle

The manager registers one retained task per original child before yielding to the caller. Dropping a qualification wait does not drop the supervisor or its cleanup result. Every provider await is bounded by the original monotonic deadline and a cancellation signal. Profile/device authority and canonical parent, child, resource, account, and permanent fences are rechecked around qualification and while the process is idle.

Logout and owner retirement synchronously close the manager and signal its tasks. Native shutdown and source migration await the actual retained task results before canonical workers close. A lost or unproven process result remains a sticky failed drain, including when the manager has no executable entry. Adoption separately rejects retained runtime history.

The supervisor alone produces a non-deserializable process observation. Its evidence sink consumes the original issuance custody and binds the exact process source. Cleanup evidence may be written after profile retirement, but cannot create another process, requalify it, or free tokens. A start failure records only `unknown`; no missing startup acknowledgement is translated into `not_started`. Issued history is permanently non-reissuable.

## Trusted launch and shared configuration

The launcher accepts the native selected dedicated keychain profile or the exact trusted shared `CODEX_HOME` selection. It uses a private qualification directory, fixed instructions and no-tools overrides, cleared environment, and the retained guardian. It does not call the legacy shared-profile metadata subprocess or reuse the legacy web-enabled policy.

For shared configuration, a read-only canonical preflight checks the current native child, original reserve receipt, resource/provider binding and finite delivery. Already-issued or uncertain history cannot authorize another inspector. A separately retained metadata-only process reads effective configuration, derives bounded restrictive MCP and feature names, and must be observed stopped before the prepared final launch is returned. Its observation carries no account or agent authority. Invalid or injected names, unsupported origins and fixed policy mismatches fail closed. Cancellation and logout drain this inspector through the same retained task mechanism; uncertain cleanup blocks adoption. Only after this inspection does the ledger claim one-shot provision custody, rechecking current authority.

Qualification checks the actual final retained app-server's effective configuration twice and repeated authenticated quota-account observations. The quota identity must match the canonical reserved resource's provider account. Unknown enabled features, MCP, web/tool access, changed account, unsupported origin, or unresolved configuration fail qualification and stop that original process. Inherited settings that change after inspection are therefore not silently accepted. There are no thread/turn methods in this manager.

The launcher preserves the existing ADR-029/native Host observed-supervision contract (`require_crash_containment=false`). The initial implementation incorrectly requested a stronger platform guarantee for this closed metadata operation; that extra condition was removed. The platform still refuses callers that explicitly request full POSIX crash containment. This path relies on retained guardian custody, exact observed descendant cleanup and sticky unknown outcomes; it does not claim universal containment after simultaneous host/guardian loss or adversarial unobserved descendants. No platform implementation or requested-guarantee refusal was weakened.

The concrete precedent is `native/hagency-execution/src/host.rs::launch`, which sets the same observed contract. `native/hagency-platform/src/supervisor/unix.rs` cancels the retained scope on owner EOF, invalid control or leader exit; macOS `supervisor/unix/macos{.rs,/native.rs,/tracking.rs}` starts suspended, captures identity and ancestry before resume, and signals only proved ownership. ADR-029's 2026-09-20 amendment explicitly preserves the product's limitation for an unobserved daemonized descendant. Unknown or failed census/stop evidence remains unknown. Windows' retained Job Object and optional Linux cgroup recovery have different guarantees; neither is synthesized by this adapter. A future request for stronger crash containment needs a separate explicit platform design and acceptance, not an implicit new prerequisite for the existing metadata workflow.

Feature discovery accepts Codex's boolean, structured and nullable feature representations only to produce literal `false` overrides. In particular, upstream `FeaturesToml.network_proxy` is an optional value that can serialize as null. Neither a missing/unset value nor a configuration table counts as an already-disabled feature. The final retained process must independently return boolean false for every feature entry, alongside the fixed disabled feature set. Override names and final argument bytes/counts are bounded before native issuance.

The explicit installed-provider acceptance test uses the selected shared configuration, a fresh isolated HOME/work directory, and the same production launcher/inspector/qualification routines, without a test-only containment override. It never opens a NativeOwner or locks the running UI profile, copies credentials, changes provider selection, claims resources, or sends model work. It checks the protected selection, configuration and authentication files are unchanged, and observes both exact processes stopped. Provider-owned transient caches/logs may be written by ordinary metadata RPCs. This test is separate from the offline protocol-fixture regressions and is not evidence of prompt execution, billing settlement or persistent agent readiness.

## Selected-provider validation checkpoint

The installed Codex 0.162.1 selected shared profile passed three consecutive metadata-only acceptance runs from one frozen native test binary. The same production launcher was used, without a test-only containment override. Both original processes stopped, stable authenticated quota identity and effective no-tools settings were observed, and protected provider-selection/configuration/authentication bytes remained unchanged. No model turn was sent.

A real repeat exposed a two-second network metadata timeout. Account/quota reads now use the remaining original monotonic lease, bounded by the same cancellation/deadline checks; no response extends that lease. A supervised fixture with two 2.2-second quota reads covers this change. Startup expiry and qualified-process expiry are separate tests: the latter must first report live, then stop at its original deadline without another spawn.

Focused results: runtime policy discovery **8/8**, canonical store runtime **13/13**, native HTTP/process transport **15/15**, installed-provider repeat **3/3**. Evidence and exact source/test/probe hashes are retained under `.run/managed-runtime-selected-provider-final/`. The earlier logs retain the diagnosed failures (old fixture binary, a one-second success-precondition race, and the corrected real RPC timeout). A prior parallel supervisor fixture also returned unknown cleanup under concurrent process load; bounded rerun passed without changing the conservative unknown behavior. These focused results do not claim a broad performance/stability soak, persistent readiness, model execution or billing completeness.

## Next execution boundary

Persistent shared agents need a renewable activity/idle lease for the same retained process, separate from the immutable one-shot spawn command. Renewal must not reissue an uncertain command or authorize a replacement process. The next slice must connect real provider usage and terminal evidence to canonical conservative accounting, assigned-project-admin admission, prompt/work delivery, Matrix replies, stop/revoke, and recovery. Process exit alone never proves billing completeness or capacity release.
