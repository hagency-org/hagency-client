# Native integration required after project request approval

Date: 2026-10-16. Status: additive native ledger foundation implemented; production transport, owner confirmation, migration and allocation UI remain unconnected. The current mini app supports project request intent and server administrator approval. `allocationStatus: awaiting_allocation` does not represent a reserved budget, an executable project, or an agent. Keep `project-reservations-v1` disabled until the integration and reconciliation gates below pass.

Companion server design: `hagency-server/docs/design/hagency-management-allocation-next.md`. The authoritative migration direction remains Hagency Desktop's `docs/design/hagency-management-contract.md`.

## Native foundation checkpoint

`hagency_store::owner_resources` adds one owner registry using the existing `DomainRepository` writer and resource/seat accounting. `OwnerResourceRegistry::open()` uses the OS account's home from `getpwuid_r`, not `HOME`, an app data directory or a Matrix profile path. Its private directory is `.hagency-owner-resources`. A caller cannot select a production alternative. Same-process handles share one writer; a second process fails with `Locked` while it is owned, and after restart sees the same committed holds. There is no management web listener or new local IPC service. Windows/mobile account-root adapters are not accepted by this desktop foundation; unsupported ownership environments fail closed.

`ProfileAuthority` is a native-only, expiring, revocable handle. The Desktop adapter must derive its digest/account from the authenticated SDK context, retain it for the matching authorization generation, and retire it on account/package changes; strings supplied by Splash are not proof. Closing one profile must retire that profile's authority, not call the registry's global `shutdown`. The latter is for installation-writer shutdown.

`VerifiedProviderAccount` requires a verified stable provider quota-account subject and fixed provider issuer. Its account digest excludes runtime, model, credential home and Matrix identity. Codex and Claude presets accessing that same verified account share one `Seat` declaration. Unknown identity cannot create capacity through this API. Explicit native-owner consent may link a profile to an existing owner resource; it does not infer another account or increase its ceiling. The real provider identity adapter, provider-issued identity normalization and owner-mediated migration are still missing. Passing a provider path as this subject would violate the API contract.

`prepare_enrollment`, `prepare_link` and `prepare_revoke` return non-deserializable, non-cloneable `OwnerResourceConsent`. Consuming it rechecks the captured authority before committing and when returning the result. Profile ACLs grant access to specific resources, while private management journals and their existing account/device bindings remain separate. The registry refuses to adopt a populated legacy/profile database implicitly; copied registry directories and symlinks cannot supply another authoritative root.

`VerifiedManagementEnrollment` binds the native profile, accepted enrollment/contribution, resource/revision, admitted coordinator and executor installation/generation. `prepare_capacity_grant` then returns a separate native `OwnerGrantConsent`. The first version writes an immutable monthly UTC grant and its durable receipt; it has no amendment, renewal or parent-grant refund API. `recover_capacity_grant` retrieves that original receipt under fresh authorization for the same profile and installation without another human approval or a new hold. Serialized grant receipts are capped at 12 KiB before commit, leaving room within the central 16 KiB publish envelope. Delegation expiry matches the central maximum of 366 days. Native consent is not yet exposed in Desktop and no new allocation capability is advertised.

The native consent now exposes a frozen `OwnerGrantPeriod` through `period()`:
the exact UTC key, start and end that the trusted screen must display alongside
the selection. Preparation reads the native clock; no public arbitrary-time
setter exists. A new grant checks that period after acquiring the writer and
again immediately before commit. Crossing a UTC month boundary invalidates the
confirmation and rolls back its hold, receipt and ledger revision. Monotonic
consent/provider/enrollment expiry remains a separate fence, including after
the worker returns. A committed effect whose short authority expires before
response delivery returns `OutcomeUnknown` and retains its original receipt.

Only new local grant-command digests include the reviewed period. Published
`NativeGrantReceipt` fields and stored old receipts do not change. Recovery by
the original grant ID remains read-only, including old command digests that
predate the period field. Reusing that old command ID with a freshly prepared
period may conflict; callers must recover the original result rather than
reinterpret it or create a replacement hold. UTC rollover does not release an
old parent commitment.

`owner_capacity_grants` extends the existing resource/seat ledger. Its commitments participate in `budget_with_grant`, admission headroom and usage `reserved` totals alongside original agent and coordinator holds. Project children consume this parent hold once and never add another provider-level charge. A unique `(grant_id, project_id, project_revision)` prevents new delivery IDs from duplicating an uncertain reservation. There is no competing allocation calculator or separate budget database.

`VerifiedAllocationDelivery` can be constructed only by the trusted native server transport after validating an exact executable command and current lease. An `executionAllowed: false` historical recovery response cannot produce it. The reserve path checks the frozen coordinator, eligible manager, semantic resource identity, delegation, UTC period, executor generation and parent headroom. The release path permits cleanup under fresh authorization for the same original owner/profile/installation/contribution/resource even after configuration or generation changes. Release-before-reserve writes a tombstone; delayed reserve cannot recreate that hold. Every newly recorded result increments the shared ledger revision; original-command replay returns the original receipt and revision. Historical recovery is read-only and checks the original profile and installation.

This foundation has no execution/agent attachment API. Current child release can therefore return all of an unexecuted child's capacity to its still-held parent. Before adding execution, atomically retain agent reservations, consumed and unknown usage and final settlement; do not reuse that zero-retained cleanup behavior for running agents. Parent holds deliberately survive access revocation, UTC rollover and child release until a separately reviewed settlement/refund flow exists.

Focused tests use isolated temporary ledgers and synthetic provider subjects. They cover concurrent profiles on different homeservers, two models/runtimes on one account, actual second-process exclusion followed by restart and overflow refusal, denied profile access, legacy holds retained, child/replay conservation, replacement IDs, release tombstones, generation/config/period changes, closed wire digests and pre-effect size/expiry rejection. They do not establish that real provider identity, legacy migration, background transport, trusted Desktop confirmation or the mini-app allocation flow is complete.

Before activation, reconcile every applicable existing profile/legacy ledger and pending receipt into explicit owner mappings. Merely leaving the old ledgers untouched does not make their holds visible to a fresh owner ledger. If the native host cannot establish that reconciliation or the provider's stable quota identity, it must keep allocation unavailable. The current foundation's test that already-reconciled legacy holds share the same seat is a conservation test, not an automatic migration implementation. Also preserve original native grant command custody through publication recovery: a central revision conflict may permit republishing the same immutable native receipt after canonical binding checks; it must never create a replacement parent hold.

## Exact types and the missing mapping

`ResourceGrant` contains `id: ResourceAllocationId`, `server_engagement_id: ServerEngagementId`, native `resource_id`, `revision`, `allocated_tokens`, and `eligible_managers`. `ResourceConfigurationAccess::prepare_contribution` returns a non-deserializable command carrying the owner's expiring, revocable gate. `DelegationChange` adds the expected delegation revision, selected coordinator, expiration, `allow_self_approval`, state and restricted export recipients.

`ProjectApproval` and `ProjectGrant` are re-exports of `palpo_hagency_contract`. The existing project grant contains the project identity, engagement, revision, owner, resource allocation IDs and state. **It has no per-project token reservation.** `approve_coordinator_project` authorizes a project to use existing allocations; agent approvals consume their capacity later. Directly translating `ProjectPlan.requestedTokens` into this grant would falsely advertise a reserved project budget.

The existing `coordinator_resources` schema has `UNIQUE(engagement_id,resource_id,period,period_key)`. It cannot represent several dedicated resource allocations for different projects against the same resource/engagement/period. The recommended extension is therefore a project reservation child in the same ledger, with a project ceiling, conservation against the parent allocation and atomically retained agent reservations. A dedicated-resource-allocation alternative would require an explicit schema and conservation-model change; it is not an adapter-only solution.

A UI convention or matching allocation label does not enforce a project reservation. No new parallel ledger should compete with `coordinator_resources`, agent holds, account ceilings or usage settlement. Resolve how the existing engagement contribution amount relates to a requested project amount without charging the same commitment twice.

The enrollment authority also needs a typed adapter. `coordinator_engagements.id` is a foreign key to legacy `registrations.fleet_id`; `current()` requires that registration's generation and reception room. `hagency_core::authority::Registration` validates the legacy `hf_` plus 32 hexadecimal identifier and its representative Matrix identity. A new `con_*` admission plus execution-device authorization cannot be inserted as this legacy registration. Extract the shared ledger authority checks behind explicit legacy-registration and management-enrollment proofs, preserving the existing Matrix verification path. Do not invent a representative/reception room or weaken the old validator to bypass the missing proof.

The new central `management_projects.id` is currently a request-plan ID, not an existing executable project ID. Persist a mapping from that ID and revision to the actual Matrix project, engagement ID/generation, allocation ID/revision, executor device/generation, coordinator delegation revision and original command IDs. Never derive it from a resource label, project name or hostname.

## Confirmed cross-profile capacity isolation gap

Read-only code inspection confirms that the current embedded resource ledger is selected by Matrix authorization profile, not by the physical provider account. This is an allocation blocker, not a completed cross-profile resource design:

1. Hagency Desktop `src/hagency/backend.rs::Service::for_current` selects `app_data/native-owner/<hash(origin,owner)>`.
2. `NativeOwner::management` in `console/native/management.rs` selects `owned-agent-owners/management_<profile>/domain.sqlite3` under that root. `console/owned_agents.rs::profile_identity` hashes origin, issuer namespace, subject and owner. Different homeservers, different Matrix owners or a changed subject therefore produce different databases.
3. `console/owner_provider.rs::Operation::UseLocal` may explicitly associate either profile with the same trusted canonical `CODEX_HOME`. Its `selected_reference(..., shared=true)` is a digest of that shared provider home, independent of Matrix identity. Separate profile provider homes do not imply separate underlying provider subscriptions when this mode is selected.
4. `management/connection.rs::provider_seat` hashes Matrix `context.account` together with runtime and the native credential reference. Two different Matrix accounts using that same local provider reference obtain different `seat_embedded_*` IDs.
5. `management/enrollment.rs` constructs a new resource preset/ceiling, and `domain/resource_configuration.rs::enroll_management_resource` writes the embedded seat with `declaration: None`. This does not create a shared provider-account ceiling or managed-account association. The restored `managed_accounts` path has random `account_*` identities and a per-ledger deployment/HMAC key tied to its private directory; it is not a cross-profile registry for these embedded seats.
6. `domain.rs::headroom_with_grant`, `check_grant_within` and `domain/coordinator.rs::additional_commitments` see only the selected SQLite database. Its `domain.lock` excludes concurrent writers to that directory, not writers to a different profile directory. Existing same-ledger parent/child conservation tests do not cover two profiles.

Consequently, profile A and profile B can each enroll a resource with a 100,000-token monthly ceiling against the same connected provider account. Both definitions can show their independent uncommitted ceiling. Wiring allocation separately to each ledger would allow each to reserve its full 100,000 without seeing the other profile's hold. Sequential account switching does not remove the persisted commitments; two application processes with separate data roots make the same isolation more obvious. Current project request E2E has not exercised this oversubscription because shared reservation is not implemented yet. No real provider account or profile was modified for this review.

Removing the Matrix account from the seat hash alone is insufficient: identical seat IDs in two databases still do not share commitments. Pointing both profiles to the same managed database is also not a safe quick fix: `DomainRepository::open_managed` deliberately rejects a different `management_identity.profile_digest`, and those checks protect private commands and account data. Do not disable that binding or merge profiles merely because their Matrix localparts or provider-home strings look similar.

Before shared allocation, introduce a native owner/resource-account identity and one authoritative reservation ledger outside individual Matrix profile directories. Matrix profiles remain separate principals with explicit local-owner grants to particular resources and engagements. A trusted native enrollment action must authorize linking a second Matrix profile to the existing resource; knowing its identifier must grant no access. Keep private profile journals/projections separate where appropriate, but their allocation effects must resolve to the same physical resource/account writer.

The resource identity should bind the trusted local owner, provider kind and native verified provider-account/namespace identity. A path or credential-reference string alone is not proof that two credential homes represent different subscriptions; conversely, matching provider accounts must not silently merge two humans' authority. Where the provider lacks a trustworthy account identifier, require explicit native owner mapping and state the resulting accounting limits. Retain existing private-file, no-follow, keychain and provider-witness checks. Do not expose credential references or paths to Splash.

Multiple legitimate application processes using that owner resource need a single writer/registry or a bounded authenticated local coordination mechanism. Preserve the requirement of no deployed local management web server. Independent application data directories must not each claim sole enforcement over an already enrolled provider account; either coordinate through the same native registry or explicitly refuse a conflicting enrollment. This guarantee covers managed allocations, not arbitrary external provider use or a hostile OS owner deliberately bypassing the application.

Migration must enumerate all profile ledgers, recover pending command effects and retained/unknown holds, and reconcile them into one owner-controlled mapping before declaring available capacity. Never add the old independent ceilings together as if they were separate real accounts, silently discard reservations, or transfer a profile's credential access while merging accounting.

## Proposed integration order

1. The resource owner explicitly authorizes an engagement contribution and coordinator delegation from the native mini-app flow. Native code resolves the actual provider/resource/account binding and commits the grant and its publishable receipt. Merely naming a coordinator in a server admission form is not this native delegation.
2. The server administrator decides the manager's project request. Preserve the current request receipt and decision. This remains project admission; it must not reserve capacity on behalf of the resource owner.
3. The currently delegated coordinator selects capacity under the owner-approved grant. Central work records bind the approved plan and all expected revisions. Delivery targets the exact enrolled executor; no reusable credential, caller-selected URL or filesystem path enters Splash.
4. The executor checks the latest owner delegation, provider/resource binding, registration generation, project mapping and shared parent ledger. It records the original delivery, atomically reserves the chosen capacity and writes the resulting receipt/publication. Lost replies are recovered using that original identity. A reserve failure is explicit and leaves the plan unallocated.
5. The central server acknowledges the verified executor result and reports allocated capacity with observation time and period. It never reports allocation merely because the delivery was queued. An old acknowledgement cannot erase a newer native publication.
6. Matrix room/setup work uses its own durable setup identity and actual Matrix observations before declaring the project ready. This is an automatic executor verification/provisioning stage, not another human project approval. A pending, failed or uncertain setup must retain the original allocation and expose its recoverable state.
7. Once project capacity has been allocated, the administrator assigned to that project decides agent creation requests. The resource coordinator's human decision is project capacity allocation, not a second approval of each agent. The executor automatically validates the project administrator's decision and current capacity/delegation/device constraints before reserving agent capacity. Keep the server's personal-owner/device foreign key path intact; introduce explicit shared assignment checks across claims, tool authorization, replies, stop, revoke and cleanup. This integration is still separate work.

The legacy `approve_coordinated_agent` path calls the shared contract's coordinator-actor approval checks. It cannot be reused unchanged as the new product's human approval flow. Add an explicit business-authority adapter that proves the deciding administrator is assigned to this project, binds the original agent request and project allocation revisions, and then invokes the retained reservation/receipt mechanics. Server-wide project admission authority, resource coordinator capacity authority, and assigned project administrator agent-admission authority are separate roles. Do not substitute the Hagency resource owner/coordinator for the assigned project administrator or require another human vote at the executor.

The current legacy `ProjectDefinition` requires actual room IDs before `approve_coordinator_project`, whereas the new intent may have no Matrix project yet. Server and native design must choose and test the provisioning order, including cleanup of rooms created before a capacity failure. Do not insert fake room IDs or mark ready to make the old method accept a new intent.

## Provider and workspace consent gates

Current `NativeManagement::connect_provider` associates an already signed-in supported local provider. The desktop `ProviderConsent` is constructed by the trusted host, expires, binds the Matrix account and exact package lease, and is consumed once. Splash cannot pass `approved`, credentials, arbitrary paths or login URLs. Fresh provider sign-in is still missing from this mini-app slice.

`verify_local_resource` obtains the actual provider model/account status and constructs a short-lived `ProviderWitness` in native Rust. It checks the original model, reasoning, resource revision and private credential reference. The mini app receives only a public status projection. Connection verification is not permission to create an execution workspace or start a provider turn.

The personal owner path currently validates/canonicalizes a configured workspace in `console/owned_agents.rs`, creates managed workspaces through `owner_provider::prepare_workspace`, and uses scoped room files and runtime permissions in `console/owned_runtime.rs`. The mini app does not yet expose a trusted workspace selection capability. The shared path must retain those native boundaries: explicit native selection or clearly identified managed workspace, current account/package/device scope, no script-supplied host path, and no silent directory takeover. Resource allocation alone must not grant arbitrary host filesystem access.

The next allocation implementation should accept opaque native provider/workspace choices, never raw `credential_ref`, provider home or `workspace_root` from Splash. Account switching, package closure and expired confirmation must prevent queued consent from authorizing a later operation. Background executor enrollment needs independently revocable authority rather than retaining an invisible human UI session.

## Custody to preserve when extracting remaining personal services

`console/owned_agents/commands.rs` persists private profile-scoped `agent.create` and `agent.bind` intents before the server mutation. It preserves original payload/key, rejects a replacement key for an equivalent pending command and reads original server status during recovery. `console/native/configuration.rs` maintains device-pinned work/completion receipts, current scope checks and a background recovery worker. Replacing these flows with direct central HTTP calls would lose existing recovery semantics.

`NativeOwner::Command` still contains `CreateAgent`, `BindAgent` and `CreateMatrix` variants with `serde_json::Value` payloads and an in-memory console adapter. Do not expose that enum as a generic mini-app entry point. Extract closed service DTOs and trusted host operations first, preserve the original journals, and make HTTP handlers thin adapters. The already added management journal remains the owner/installation command-custody boundary for the new services.

## Required acceptance before claiming allocation

- Concurrent project reservations across two server engagements sharing one account/resource cannot exceed the real parent ceiling. Test two Matrix homeservers/profiles and two separate application processes/data roots against the same explicitly linked provider account, not merely two engagements already in one SQLite fixture. Verify each authorized profile sees only its allowed objects while both reservations consume one owner ledger; the second over-capacity reservation must fail.
- Test restart/account switching, provider credential rotation and two credential homes for the same provider account. Ensure mapping does not duplicate a parent ceiling, silently merge unrelated owners or erase unknown holds. A second process unable to obtain the authoritative native writer must fail safely instead of creating an independent budget.
- Lose the server reply, kill the executor after reservation commit, restart with fresh authorization and recover the original allocation without doubling the hold or changing its command ID.
- Change owner delegation, coordinator, resource/model revision or device generation while work is queued; old work must fail safely and central status must identify the stale prerequisite.
- Withdraw/revoke while a reserve or setup acknowledgement is in flight; no stale acknowledgement may reactivate the project, erase cleanup or free unknown usage.
- Verify correct per-project budget accounting, resource contribution accounting and period rollover with known spend, unreported usage and multiple agents. Display available/total plus measurement age; never invent live capacity from the plan amount.
- Confirm the server administrator's project admission decision and resource coordinator's project capacity decision are not repeated at the executor. After allocation, an agent creation request succeeds only with the administrator assigned to that project; an unassigned server administrator, resource owner or coordinator does not acquire that authority from their other role. Native resource/ledger checks are automatic and never introduce another human agent approval.
- Test declined/expired native provider and workspace prompts, profile switching, package retirement, no local listener and no secret/path leakage into Splash, logs or Matrix notifications.
- Drive the production mini app with separate owner/coordinator/manager/admin identities and inspect native Makepad screens for pending allocation, refusal, unknown outcome, ready and revoke cleanup in English/Chinese and light/dark themes.

None of these new allocation acceptance cases are implied by passing the current project request or legacy native unit tests.

### Existing-provider identity observation

`NativeManagement::verified_provider_account(ManagementRuntime)` returns only the native, non-serializable `owner_resources::VerifiedProviderAccount`. The current package must have `ReadProviders` and `ConnectProviders`; the authenticated Matrix context and both grants are checked again after provider I/O. The method neither declares capacity nor merges a legacy ledger. Owner registry consent remains a separate native step.

For Codex, an identity-only child reuses the selected provider-managed sign-in, pins and verifies the effective built-in OpenAI backend, and reads the public `account/read` and `account/rateLimits/read` APIs. Three consistent signed-in account metadata observations bracket two identical usage `accountId` values. The registry subject is `openai.chatgpt` plus that opaque backend account ID. Email is only a switch detector; local path, credential reference, runtime and model never distinguish a second quota account. The child has a 25-second overall deadline and cannot request login or inference. No token, credential file or raw account identity enters the mini-app response.

This depends on a Codex version whose authenticated public usage response actually includes `accountId`; generated protocol schemas are not proof that a particular installation/backend will supply it. Missing IDs, malformed or changing authentication, unsupported backend origin, or an older protocol fail with a bounded identity-unavailable error. Claude's inspected public auth-status response exposes email and organization ID but no stable individual quota-account ID; Octos profile metadata likewise provides no suitable proof. Neither is treated as an independent account on this evidence.

The proof is a short-lived observation, not a guarantee about a future agent turn. Before activation, the execution adapter must revalidate that the selected runtime still uses the same registry account. Existing legacy holds still require explicit source-fenced reconciliation, and no current resource is automatically imported into the installation ledger. The parent-grant settlement and owner confirmation flows remain separate gates. Synthetic process tests exercise public read ordering, protocol/identity changes and unsupported auth without reading a real provider profile.

### Native allocation transport checkpoint

`console/native/allocation_transport` now provides a typed native transport for the existing owner registry. It is deliberately absent from the mini-app capability catalog and is not started by the host. Server allocation/parent feature flags remain unchanged. This is transport qualification against isolated ledgers and an actual localhost HTTP fixture, not activation of a production enrollment or completion of the migration.

The Rust API is `AllocationTransport::new(Arc<NativeManagement>)`, then:

| Method | Required native permission | Purpose |
| --- | --- | --- |
| `publish_grant(registry, command_id, grant_id, expected_contribution_revision)` | `PublishGrants` | Publish an existing immutable native receipt; never create a hold from caller data. |
| `retry_publication(registry, command_id)` | `PublishGrants` and `ReadIntents` | Recover the original private journal input and central command before retry. |
| `poll_allocation(registry, after)` | `ExecuteAllocations` | Apply a leased project reserve/release command or report its existing local receipt. |
| `recover_allocation(registry, command_id, command_digest)` | `ExecuteAllocations` | Report historical local results; cannot authorize execution. |
| `poll_parent_settlement(registry, after)` | `SettleGrants` | Apply a leased parent close/settle command in the same ledger. |
| `recover_parent_settlement(registry, command_id, command_digest)` | `SettleGrants` | Recover historical parent results without a new effect. |

Fixed-route closed DTOs mirror the central allocation and parent-settlement contracts. A command must match its canonical digest, original local grant, owner/profile, stable device installation and current authorization. Enrollment IDs come from the stored native grant, never from a contribution ID or invented legacy registration. Reserve requires the original generation and current semantic bindings. Cleanup permits same-installation reauthorization while retaining the original receipt identity. Native parent closure uses the permanent shared-ledger fence and conservative liability accounting already implemented in `owner_resources`.

Execution and reporting leases expire at a monotonic deadline computed from the request send boundary; slow responses cannot extend authority. Historical recovery explicitly rejects `executionAllowed=true`. Uploads have the same finite deadline. A malformed acknowledgement, timeout or lost response leaves the original local receipt intact. A saved publication success remains immutable while recovery returns the latest server projection. Another command ID cannot replace a publication whose outcome is still unknown. Only server-audited first-attempt nonapplication errors can end publication custody; a later rejection after an uncertain attempt remains pending. Such rejection never releases the native parent hold.

The host must synchronously retire the captured `NativeManagement`/`NativeOwner` session when its SDK account epoch changes. The registry checks that native session/device fence inside its SQLite writer, including after queue waits. Async SDK source checks before and after HTTP/ledger boundaries are additional checks, not a substitute for synchronous retirement. A source-only account change without host retirement cannot be detected inside a synchronous SQLite transaction; integration is blocked until that lifecycle invariant is established. Publication journals stay profile-private. The production registry opener remains tied to the canonical OS-owner root; the alternative isolated opener is compiled only with the disabled-by-default test-support feature.

Focused tests cover lost publication replies, original-command custody after restart, immutable first replies with current revoked projections, unknown replacement refusal, exact fixture digests and closed decoding, delayed uploads, false historical execution, generation-rotation cleanup versus stale reserves, SDK changes during server replies, permission denial, and retirement of the actual captured management session while a SQLite writer is blocked. They do not prove execution-time provider identity binding, discovery of every legacy ledger, source fencing/adoption, or a real mini-app allocation flow. Those remain activation prerequisites.
