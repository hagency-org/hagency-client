## 独立读回

PostgreSQL 读回新项目恰有 3 张任务：最终均为 `done`，版本分别为 6、7、3。第 3 张卡关联第 1 张父卡；两张 B 任务与 A 场地卡的负责人分别正确；父卡日历日期和已勾选检查项持久化，归档恢复后的卡没有残留归档时间。冲突尝试没有覆盖 B 的标题。

真实 Matrix `/rooms/{roomId}/messages?dir=b&limit=100` 读回 4 个唯一消息事件：B 的两条进展消息、A 的一条回复及一条文件消息。原生端附件下载 SHA-256 为 `4a39e4e8524e97cf4af69308ee6988ea48e404323d3dbe39e2113b0f4b60f856`。账号 ID、房间 ID、事件 ID 和 SQL 原始结果仅留在本地运行证据中。

## 发现的问题（未在本轮扩展修改）

1. **Status 与 Save 的行为不一致。** 选择 In review 后下拉框显示该值，但点击 Save 会关闭弹窗，服务端仍是 In progress，版本也不变。原因已定位：已有任务的 `move_state` 仅被 Move to top / Move to bottom 消费；`save_task` 的无修改分支直接关闭，Update 本身不包含移动。短期应把字段明确标为“移动到”，或把状态变更纳入明确、可恢复的保存流程，继续保留 WIP、版本和幂等保护。复现两次；通过 Move to bottom 则实际移动成功。
2. **重启后同一文件消息显示两行。** B 重启后的聊天界面显示两条同名、同大小文件行；服务器历史中只有一个 `m.file` 事件，A 的日志也只有一次 attachment send。问题位于原生历史/本地缓存呈现链路，需要追踪 SDK timeline 与 UI 列表的去重和恢复；本轮尚未断定具体函数根因，不能当作服务端重复发送。
3. **加载最新版后冲突提示残留。** 明确丢弃测试草稿并载入 B 最新版后，旧的“草稿已保留”提示仍显示。`reload_latest` 重置 conflict 后 select，但没有清理现有 notice，提示与当前状态不一致。
4. **展示名不统一。** “周予 · 内容与现场”在聊天和账号区域正常显示，看板负责人和评论作者仍显示账号名，长账号在窄窗口中截断。
5. **性能需专项分析。** 两个 debug 原生进程在空闲采样中各约 90–110% CPU；看板自动化操作多次耗时 8–20 秒。此数据包含 debug 构建和自动化开销，不等同于 release 性能结论；应独立测量空闲重绘、脚本调用与事件循环。聊天/项目表单交互相对较快。

聊天曾出现较长时间的“正在输入”提示，B 重启后消失；暂作为待复测现象，不认定为已定位缺陷。新建讨论房间成功后回到项目列表而非新房间，也是可改进的导航体验。
