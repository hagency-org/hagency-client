# 双用户问题修复与看板列验收（2026-10-28）

## 范围

本轮在 Client、Server 的 main 上继续修复上一轮真实双用户验收发现的问题，并补齐列的新建、拖动排序、归档与恢复。完整本地 Server、两个独立普通账号、两个独立原生 SDK 数据目录和同源构建沿用上一轮；测试项目为虚构的“街角共读 · 社区读书会筹备”。没有使用管理员绕过成员权限，没有调用 Agent 或模型。

## 根因与实现

- **Status + Save：** 原生 Status 下拉框原先只设置移动目标，Save 的 Update 请求没有状态字段，无其他修改时还会直接关闭。现在选择即形成 dirty 草稿，Update 可同时携带状态与正文等字段。Server 在同一看板锁、事务和任务版本中检查权限、列状态、WIP 并保存；失败不留下部分修改。同一幂等键保留原始回执。草稿 dirty 时不允许另一路 Move 操作抢先移动；轮询不覆盖选中的草稿状态。
- **消息重复：** 真实 Server 历史和 sync 没有重复发送；SDK 恢复后 timeline 曾出现 17 个远端行、16 个唯一事件。不能删除 SDK 原始向量中的重复行，否则后续按位置的 VectorDiff 会错位。原始向量继续完整应用差分，仅 UI 投影按事件 ID/事务 ID 唯一化，优先远端明文；重映射锚点、定位和缓存失效范围。两个正文相同但事件 ID 不同的消息仍显示两条。
- **旧提示和展示名：** 选择任务及加载最新版清理旧 notice；Space 的当前成员状态在原有授权读取中提供展示名，无需每张卡额外请求。卡片、负责人选项、子任务、评论和通知优先展示名，同名选项附完整账号区分，缺失时回退账号本地部分。
- **列生命周期：** 新建列先进入 Columns & WIP 编辑，Save columns 提交；拖动列头 `≡` 手柄调整活动列顺序。Archive/Restore 也是明确保存的配置操作，使用看板 sequence 防止并发覆盖。归档列隐藏，原卡片和内容保留；归档列内任务只读，不能新增或移入，恢复后可继续使用。最多 12 列，至少 2 个活动列且至少 1 个活动完成列。数据库迁移 v4；Client / Server 同时升级，发现能力为 `project-board-v4`。

## 性能实测与边界

上一轮空闲两端约 90–110% CPU。逐层事件计数定位到约 120 次/秒绘制，期间无动画帧、无业务 Actions，也没有 shader 时钟重绘。进一步对非绘制事件追踪，发现全局后台 Signal 被项目树、账号栏、聊天信息页、移动端/历史面板和顶部更新覆盖层无条件当作“内容变化”。隐藏组件同样收到 Signal；绘制产生的资源工作完成又带来新 Signal，持续刷新。

现在上述组件仅在实际数据/状态变化时刷新。缓存稳定的导航选中状态、项目行样式、标题栏主题与管理页导航；Skeleton 和 Spinner 在不再绘制时停止调度。回归覆盖“重复无关 Signal 不再绘制”以及“真正更新状态变化仍刷新”，不通过静默忽略实际更新来降低 CPU。

同源 debug 原生 A/B 同时打开该项目看板，停止 UI 操作 15.01 秒，以各进程累计 CPU 时间差采样，分别为 **6.33% / 8.13%**（一整核=100%）。空闲计数多数秒为 0 次绘制，数据更新时偶有 1 次；本轮最终打开项目/切换看板的自动化调用约 0.5–1.3 秒，区别于上一轮多次 8–20 秒。这是本机 debug 场景的改善证据，不是 release 性能或大规模数据压测结论。保留显式 `HAGENCY_UI_IDLE_TRACE=1` 的 debug 事件计数诊断，只输出计数和渲染标志，不输出消息或凭据。
